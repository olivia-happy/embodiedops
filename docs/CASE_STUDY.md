# EmbodiedOps 案例研究：把机器人失败变成可验证的产品闭环

## 1. 问题与用户

桌面抓取任务常被记录为 success/fail，但机器人产品经理、算法工程师和测试工程师需要的是可行动的解释：问题发生在哪一阶段、数据是否支持这个判断、什么实验能区分两个可能的根因、何时不应该继续推进。

EmbodiedOps 服务三类用户：

- **测试/数据运营**：导入经过许可、脱敏和版本冻结的 episode，发现高频失败阶段。
- **算法与控制团队**：查看支持证据与反例，形成可复现的仿真实验草案，而不是从自然语言猜测直接改参数。
- **产品经理/负责人**：用任务成功率、碰撞率、超时率、人工接受率与诊断耗时判断验证优先级和上线门槛。

当前公开版本只使用合成桌面抓取数据；不包含任何 Unitree、优必选、傅利叶或客户的内部数据，也不接入真实机器人的控制回路。

## 2. 工作流与数据契约

每条 episode 都绑定 `dataset_version_id`，包含单调时间戳的观测、事件和最终结果。流程为：

1. 导入不可变数据版本并校验 episode 结构、事件边界和 manifest hash。
2. 以确定性规则切分 `approach → align → grasp → transfer → place`。
3. 计算任务与阶段指标，定位失败阶段与候选事件。
4. 受控 Agent 只读取摘要与 allowlist 事件，产出候选机制、支持/反例证据、未知项和置信区间。
5. 验证器拒绝未知事件、越界时间窗、无依据数值和反例缺失；有效结果写入 Trace。
6. 由人审核 `simulation_only` 实验草案，才可进入后续仿真或真实机器人验证流程。

真实数据接入不是自动行为。数据卡必须记录来源、机器人型号、固件、任务族、授权或许可、脱敏状态、holdout 策略和删除约束；人工根因标注需要审核状态与 reviewer。没有 permissioned provenance 或 holdout 的输入，sim-to-real 评测必须拒绝给出迁移结论。

## 3. 特征工程与指标

**特征工程**将原始时间序列转为可解释的阶段特征：阶段时间窗、夹爪接触/宽度/力、末端位姿、规划可达性、碰撞/遮挡事件及事件发生的相对时间。数值由 Python/DuckDB 和确定性规则计算，模型不能写回数值、事件 ID 或最终拒答状态。

核心技术指标保留分子与分母，零分母显示为“不足以判断”而非 0：

- 任务成功率、抓取成功率、放置成功率；
- 碰撞率、超时率、阶段失败分布与平均完成时长；
- 诊断阶段准确率、事件证据 precision/coverage、未知事件率；
- 人工接受率与诊断耗时中位数。

## 4. Agent 边界

这里的 Agent 是“受限诊断编排器”，不是机器人自主控制器。

- 输入受 dataset version、episode ID 和 allowlist 事件约束；
- 无效 JSON 最多重试一次；
- `UNKNOWN_EVENT_ID`、`OUT_OF_BOUNDS_TIME_WINDOW`、`FABRICATED_NUMERIC_CLAIM`、`MISSING_COUNTER_EVIDENCE` 等错误码会使流程 fail-closed；
- 输出只能生成诊断草案和 `simulation_only` 实验建议，实验执行与真实机器人动作均需人审；
- 不保存 API key、原始模型输入、原始模型输出或思维链。

这体现的是 AI 产品中的“生成 + 规则验证 + 人审闭环”，而不是把高风险动作交给模型。

## 5. 业务 KPI、ROI 与假设

**业务 KPI** 应回答“诊断系统是否改善迭代效率”，而不是只报告模型分数：

| 指标 | 业务含义 | 当前状态 |
| --- | --- | --- |
| 成功率 uplift | 方案经批准后与基线的任务成功率差 | 仅合成固定样例 |
| 碰撞/超时率 | 安全与效率护栏 | 仅合成固定样例 |
| 人工接受率 | 诊断是否值得工程师采纳 | 未进行真人审核 |
| 诊断耗时中位数 | 从 episode 到可审阅建议的效率 | 离线样例 |
| sim-to-real 差异 | 仿真与许可真实 holdout 的指标差 | 无真实数据，必须拒答 |

ROI 的合理假设是：若高频失败根因能更快被定位，减少无效调参轮次，则可节省工程排查时间和仿真预算。计算时应以真实基线的工程师工时、仿真次数、成功率、报废/碰撞成本和人工接受率为输入。当前仓库没有这些生产数据，**不构成生产 ROI 结论**。

## 6. 上线门禁与扩展路线

**上线门禁**分层设置：

1. 数据：来源、授权、红线处理、版本与 holdout 均完整；
2. 质量：标注双审或裁决、诊断证据/拒答评测达标；
3. 安全：Agent 不可直连控制 API，实验默认仿真，关键异常保留 Trace；
4. 业务：在真实 holdout 上复核成功率、碰撞/超时护栏、人工接受率与耗时；
5. 发布：灰度、回滚条件、责任人与复盘机制齐备。

下一步不是把合成 demo 包装成生产系统，而是与拥有授权数据和仿真环境的团队共建数据卡、标注规范、离线 holdout、shadow mode 与受控 A/B 验证。
