# SignalForge AI 决策内核设计

## 1. 背景与目标

当前 SignalForge 已具备版本化数据、确定性指标、证据引用、机会评分、风险卡、反馈与 Trace，但实际运行路径尚未连接本地模型。洞察生成接口在没有 provider 时使用规则模板，前端也没有触发生成，因此当前产品本质上是可追溯统计工具，而不是 AI 决策系统。

本次改造的目标是：针对每个数据版本，生成一份聚焦单一首要问题的、可验证的决策备忘录。备忘录必须回答：现在该做什么、为什么、依据是什么、有哪些反例、还不知道什么，以及如何验证。

调试阶段只使用本地开源模型，不调用付费 API。最终成品验收后，是否切换付费模型由用户再次明确决定。

## 2. 范围

### 2.1 本期范围

- 本地模型适配器与健康检查。
- 子问题识别和证据分组。
- 单一首要决策备忘录生成。
- 引用、数字、证据门槛与结构验证。
- 备忘录持久化、API、Trace 和前端状态展示。
- 从“可实验”备忘录预填决策实验。
- 面向决策质量的新评估指标。

### 2.2 非目标

- 不实现开放式 AI 聊天。
- 不实现自主执行操作的 Agent。
- 不让模型计算或修改业务数值。
- 不自动下载大模型；模型选择在联调前根据本机资源确定。
- 不把无关联的行业事件解释为用户问题原因。
- 不调用任何付费模型或远程 AI 服务。

## 3. 核心原则

1. **事实与语言分离**：DuckDB 和固定规则负责数值事实；模型只负责语义拆分和结构化归纳。
2. **证据先于结论**：任何子问题、判断或实验建议都必须绑定当前数据版本中的证据 ID。
3. **反例必须可见**：备忘录必须包含相反证据，或明确说明当前未发现反例。
4. **未知项必须显式**：缺少人群、时间、渠道、频次或业务结果时，不得用置信度掩盖。
5. **拒绝也是产出**：证据不足时拒绝业务结论，并给出可执行的补数计划。
6. **本地模型不可用时不伪装**：不得以模板摘要冒充 AI 分析结果。

## 4. 决策状态与确定性门槛

决策状态不由模型选择，而由验证器根据证据计算。

### 4.1 可实验

同时满足：

- 当前主题至少有 3 条有效证据。
- 至少 2 条非脱敏证据支持同一个子问题。
- 完成反例检查。
- 主题的样本量、负向率、严重度和影响范围均可计算。
- 备忘录所有引用和数字均通过验证。

输出正式实验方案。

### 4.2 需补数

存在明显主题信号，但没有任何子问题达到“至少 2 条非脱敏支持证据”的要求，或关键分群字段缺失。

不得输出业务干预建议；只输出候选子问题、采集字段、目标证据数和重新评估条件。

### 4.3 拒绝结论

无法形成稳定主题信号、可用证据不足，或模型输出未通过引用/结构验证。

显示明确拒绝原因，不显示推荐动作或模型置信度。

## 5. 模块架构

### 5.1 Signal Analyzer

复用现有 DuckDB 指标与评分服务，提供样本量、负向率、平均评分、严重度、影响范围、证据覆盖和机会分。它是所有数字的唯一权威来源。

### 5.2 Evidence Grouper

输入一个主题的证据集合，调用本地模型返回严格结构化的子问题：

- 子问题名称。
- 对问题机制的简短描述。
- 支持证据 ID。
- 反例证据 ID。
- 模型认为缺失的信息。

模型不得返回自由文本之外的未知字段，不得引用输入集合以外的证据。

### 5.3 Decision Memo Generator

只接收通过第一阶段验证的子问题、确定性指标和证据摘录。它生成固定结构的备忘录，不决定数值，也不决定最终状态。

### 5.4 Memo Validator

负责：

- 验证所有证据 ID 属于当前不可变数据版本。
- 检查重复、脱敏和不存在的引用。
- 用数据库真实数字替换模型输出中的任何数值。
- 根据确定性门槛计算决策状态。
- 检查反例、未知项和下一步字段完整性。
- 决定是否允许保存。

### 5.5 Local Model Adapter

提供与具体本地模型解耦的接口：健康检查、结构化生成、超时和模型元数据。模型名称、服务地址和超时从环境变量读取。未来切换付费 provider 时保持业务接口不变。

### 5.6 Memo Repository 与 Trace

每份备忘录保存：

- 数据版本 ID。
- 模型名称和 provider 类型。
- 提示词版本。
- 决策状态。
- 完整结构化 payload。
- 全部证据 ID。
- 验证结果和拒绝原因。
- 每阶段耗时、重试次数和 token 估算。

每个数据版本只维护一份当前有效备忘录；重新生成时保留历史 Trace，不在 MVP 中提供多版本备忘录管理界面。

生成任务使用独立的持久化 job 记录，状态只能依次进入 `queued`、`analyzing_signals`、`grouping_evidence`、`validating_evidence`、`generating_memo`、`completed` 或 `failed`。服务重启时，未结束的任务标记为失败并允许用户重新发起，不伪装为仍在运行。

## 6. 决策备忘录结构

备忘录包含以下固定字段：

- `decision_statement`：首要判断；“可实验”时说明行动，“需补数”时说明暂缓行动。
- `topic`：原始宽泛主题。
- `subproblem`：经过证据验证的可行动子问题；未达门槛时为空。
- `decision_status`：`actionable`、`needs_evidence` 或 `refused`。
- `facts`：由规则层提供的数值事实及其字段来源。
- `supporting_evidence`：支持证据 ID、摘录和作用。
- `counter_evidence`：反例证据 ID、摘录和作用。
- `unknowns`：缺失的人群、时间、渠道、频次和结果字段。
- `reasoning_summary`：只描述证据如何支持或限制判断，不保存隐藏思维链。
- `experiment`：仅在 `actionable` 状态出现，包括假设、目标对象、干预、主指标、护栏指标、周期和停止条件。
- `evidence_plan`：仅在 `needs_evidence` 状态出现，包括采集字段、每个候选子问题所需证据数和复查条件。
- `refusal_reason`：仅在 `refused` 状态出现。

模型不得输出最终置信度分数。质量由证据门槛和验证状态表达，避免制造虚假精确度。

## 7. 生成数据流

1. 用户在首页点击“生成决策备忘录”，API 创建持久化 generation job 并立即返回 job ID。
2. 后台任务锁定当前数据版本，更新状态为 `analyzing_signals`，读取主题指标和候选证据。
3. 规则层选出机会分最高且数据完整的主题。
4. 任务更新状态为 `grouping_evidence`，本地模型第一阶段拆分子问题并引用证据。
5. 任务更新状态为 `validating_evidence`，验证器过滤非法引用、重复证据和不满足门槛的子问题。
6. 如果没有子问题达到门槛，确定性地生成“需补数”结果，不调用第二阶段业务建议生成。
7. 如果达到门槛，任务更新状态为 `generating_memo`，本地模型第二阶段生成结构化备忘录草稿。
8. 最终验证器注入权威数字、计算状态并检查所有必填部分。
9. 验证通过后持久化备忘录与 Trace，并把 job 标记为 `completed`；验证失败则保存失败 Trace、将 job 标记为 `failed`，但不保存备忘录。
10. 前端轮询 job 的真实状态；完成后读取当前数据版本的有效备忘录。

## 8. 错误处理

- **模型未启动**：API 返回可识别的 `LOCAL_MODEL_UNAVAILABLE`，前端显示模型服务状态和启动指引。
- **模型超时**：单阶段重试一次；仍超时则返回失败，不保存模板结果。
- **无效 JSON**：重试一次并再次执行严格 schema 验证；失败则拒绝。
- **未知证据 ID**：整份输出拒绝，不进行自动猜测或替换。
- **数字不一致**：忽略模型数字，使用 Signal Analyzer 的权威值，并在 Trace 记录 `numeric_mismatch`。
- **证据不足**：返回 `needs_evidence` 和确定性补数计划，不调用第二阶段模型。
- **脱敏证据**：可计入主题数量，但正文不发送给模型，也不能作为非脱敏支持证据满足子问题门槛。
- **数据版本变化**：生成中的版本若不再是当前版本，结果仍绑定原版本，但不成为首页当前有效备忘录。

## 9. API 与前端行为

### 9.1 API

- `GET /api/v1/decision-memo`：获取当前或指定数据版本的有效备忘录。
- `POST /api/v1/decision-memo/generate`：创建本地异步生成任务，返回 `202` 与 job ID；同一数据版本已有运行中任务时返回该任务，不重复生成。
- `GET /api/v1/decision-memo/jobs/{job_id}`：返回真实阶段、失败代码和完成后的 memo ID。
- `GET /healthz/model`：返回本地模型连接、模型名称和就绪状态，不暴露凭据。

### 9.2 首页

- 未生成：展示真实数据基线与生成按钮。
- 生成中：根据 job API 的真实状态展示读取指标、拆分子问题、验证证据和生成备忘录阶段；不使用纯客户端假进度。
- 可实验：显示首要决策、事实、证据、反例、未知项和实验入口。
- 需补数：显示“暂不建议采取业务动作”、候选子问题和补数清单。
- 拒绝：显示拒绝原因，不展示建议动作。
- 模型失败：显示本地模型状态、失败阶段和重试入口。

### 9.3 用户洞察

作为证据探索器，按备忘录子问题展示支持证据、反例、脱敏项和原文，不重复生成结论。

### 9.4 决策实验室

只有 `actionable` 备忘录可以预填实验。预填内容包括假设、证据 ID、主指标、护栏指标和建议周期；用户仍需确认负责人和截止日期。

### 9.5 风险雷达

保持独立。除非存在明确的证据关系，否则行业事件不得被模型描述为用户反馈问题的原因。

## 10. 测试与评估

### 10.1 单元测试

- 本地 provider 正常、超时、异常和无效 JSON。
- 子问题 schema 与唯一证据引用。
- 不存在证据 ID 的拒绝。
- 脱敏证据不进入模型上下文。
- 数字篡改检测与权威数字注入。
- 三种决策状态的确定性门槛。
- 反例、未知项和状态专属字段完整性。

### 10.2 API 与集成测试

- 模型健康检查不泄露配置。
- 每个数据版本只返回当前有效备忘录。
- 失败 Trace 被保存而失败备忘录不被保存。
- 服务重启后未完成 generation job 被标记为失败，并且可以安全重试。
- `actionable` 备忘录可以预填决策实验，其他状态不可以。
- 数据版本在生成过程中切换时不会污染当前首页。

### 10.3 质量评估

新增指标：

- 子问题证据精度。
- 引用完整率。
- 无支持数字率，目标为 0。
- 决策状态准确率。
- 人工行动性评分。
- 补数计划具体性评分。

当前 16 条人工审核集仅用于回归门槛，不作为生产质量声明。正式质量评估需增加包含多证据子问题、反例、脱敏、缺失字段和拒绝案例的人工审核样本。

## 11. 当前数据的预期行为

当前服务主题包含 4 条评论、3 条负向反馈、75% 负向率和 2.0 平均评分，但排队透明度与客服响应时效各只有一条明确非脱敏证据。系统应返回 `needs_evidence`，而不是建议全面改善服务。

预期首要判断：

> 服务负向信号明显，但现有证据分散在不同问题机制上，暂时无法判断应优先处理排队透明度还是客服响应时效。先分别采集午高峰等待时长、订单进度查询、客服首次响应和解决时长；每个候选子问题积累至少 3 条独立证据后重新评估。

## 12. 验收标准

1. 未配置或未启动本地模型时，产品明确报告不可用，不生成伪 AI 结果。
2. 每份保存的备忘录只引用当前数据版本中存在的证据。
3. 所有数值与 DuckDB 计算结果一致，模型不能改变。
4. 当前演示数据生成 `needs_evidence`，并给出具体补数计划。
5. 满足证据门槛的测试数据可生成 `actionable` 备忘录和完整实验方案。
6. 非法引用、无效 JSON、超时和模型数字篡改均有自动化测试。
7. 前端依据服务端 job 状态完整展示未生成、真实生成阶段、可实验、需补数、拒绝和模型失败状态。
8. 现有证据抽屉、反馈、Trace、风险来源和 Docker 本地验证继续通过。
9. 调试阶段没有任何付费模型调用或远程评论数据传输。
